# 开发顺序：先桌面体验，再手机与同步

## 背景

架构上先定同步约束是对的，但开发顺序不能照搬：用户真正每天用的是桌面端，
手机与同步是增强。若先做同步，桌面端仍然简陋，等于把成本花在少数场景。

## 决定

开发顺序调整为：

1. **桌面端体验补齐**（当前主线）：试聊、人设查看/衍生、头像裁剪、导入导出、回访承接、记忆提示、埋点；
2. **桌面端稳定与打包**：Tauri 安装包、自动更新、错误上报；
3. **手机端只读接入**：浏览器先能看同一份数据，验证配对与同步；
4. **双向同步**：消息/人设双向、冲突提示；
5. **记忆与演练同步**（最后）。

架构约束（ULID、墓碑、outbox）在阶段 1 就落到表结构里，但**不实现同步逻辑**，
避免以后迁移；这样“先做桌面”不会造成返工。

## 理由

桌面端是主场景，体验改动能被立刻感知；同步是低频增强，晚做不伤主线。
把同步所需的字段先预留，等于用很小的成本买下未来的选择权。

## 后果

- 体验 spec 重新回到主线，但需要先加 ULID/墓碑等字段（约 2–3 人日）；
- 手机端与同步排到桌面体验之后，短期不做；
- 记忆提示、回访承接不再等待同步，可以在桌面端先做。
